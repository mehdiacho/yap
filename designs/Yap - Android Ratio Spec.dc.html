Yap — Android Ratio-Based Layout Spec

Resolution-independent implementation spec, companion to Yap - Android Designs.dc.html

Every dimension below is either a fixed dp/sp token (never scales) or a ratio (scales with the device). Use this table instead of eyeballing the mockup screenshots — it removes guesswork for spacing, sizing, and color across any phone width.

0 · How to read this spec — read this first.
Two different problems get confused as "make it pixel-perfect," so this spec separates them:

(a) Density — already solved by Android's dp/sp units. Corner radius, stroke width, icon glyph size, elevation, and type size are specified as fixed dp/sp below and must not be scaled by screen width — that's what dp already does across densities.

(b) Width class — phones range ~360–430dp wide. This is the actual "different screen sizes" problem. For anything whose size should track screen width (side margins, card widths, the capture button, avatars), this spec gives a % of screen width instead of a fixed dp, so a 360dp and a 430dp phone both look like the same design.

(c) Vertical position — do not implement screen layouts with a top%/height% coordinate table. These screens are not absolutely positioned; they are vertical stacks (Compose Column) of fixed-height blocks with exactly one flexible spacer (Modifier.weight(1f)) that absorbs whatever vertical space is left. A top% table breaks the moment the aspect ratio changes (tall vs. short phone); a flex-column with one weighted spacer does not. So each screen below is written as an ordered list of blocks — sized by their own content or a % of width — with the flexible gap called out explicitly. This is the correct, robust mapping to Compose and is what makes it truly pixel-perfect across devices, not just on the reference phone.

Baseline reference device: 360dp × 780dp (matches the design mockups at 320×694 CSS px, scale 0.888). All % figures are computed against this baseline; being ratios, they hold at any width.
